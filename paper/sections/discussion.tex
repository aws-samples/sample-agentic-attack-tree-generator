\section{Discussion and Conclusion}
\label{sec:discussion}
%==============================================================================

\subsection{Design Tradeoffs}

\textbf{Parallel vs.\ sequential execution.} The parallel fan-out for attack tree generation provides significant speedup but prevents inter-threat context sharing. A sequential approach could identify cross-cutting attack paths (e.g., a compromised IAM role enabling multiple threats), but at $N\times$ cost. We chose parallelism as the default, noting that cross-threat analysis could be added as a post-processing consolidation step.

\textbf{Hybrid TTP mapping.} Pure embedding retrieval is fast and deterministic but lacks contextual reasoning. Pure LLM mapping avoids the embedding model entirely but is expensive (one LLM call per step) and prone to hallucinating non-existent technique IDs. Our hybrid approach uses the embedding for efficient candidate retrieval and the LLM only for refinement, keeping costs proportional to the override rate rather than the total step count.

\textbf{File-based state passing.} Agents communicate through JSON files rather than in-memory message passing. This adds I/O overhead but provides debuggability (every intermediate output is inspectable), resumability (a failed pipeline can restart from the last successful stage), and simplicity in parallel execution (no shared-memory synchronization).

\subsection{Limitations}

\textbf{Evaluation scope.} Our evaluation uses sample applications rather than production systems. While these applications represent diverse cloud architectures, they may not capture the full complexity of real-world deployments with legacy components, multi-cloud configurations, or custom middleware.

\textbf{Model dependence.} All experiments use a single model family (Claude via AWS Bedrock). Performance may vary across model providers, and the system's effectiveness is bounded by the underlying model's security knowledge.

\textbf{ATT\&CK coverage.} MITRE ATT\&CK, while comprehensive, has known gaps in cloud-native, container, and serverless attack techniques. Mappings to these domains may be less precise.

\subsection{Future Work}

\textbf{Automated attack matrix ingestion.} We plan to extend beyond MITRE ATT\&CK by ingesting additional threat frameworks---the Wiz cloud threat matrix~\cite{wiz-cloud-matrix}, AWS Threat Technique Catalog (TTC), OWASP attack patterns, and CAPEC~\cite{capec}. A unified STIX-based knowledge graph would normalize techniques across matrices, increasing coverage for cloud-native attack surfaces that MITRE alone underrepresents.

\textbf{Domain-specific embedding fine-tuning.} The TTP ground truth dataset built through our evaluation framework (\S\ref{sec:evaluation}) provides SME-labeled correct/incorrect mappings. These labels can be used to fine-tune a custom security embedding model starting from ATTACK-BERT, improving retrieval accuracy for the specific threat domains \threatforest{} encounters and reducing the LLM reviewer's override rate over time.

\textbf{Prompt optimization.} The SME-scored traces captured by our observability infrastructure are directly compatible with DSPy's MIPROv2 optimizer~\cite{opsahlong2024miprov2}, which can jointly optimize instructions and few-shot demonstrations for multi-stage LM programs. Each scored trace provides a training signal for the corresponding pipeline stage.

\textbf{Automated evaluation.} To reduce dependence on SME availability, we plan to develop LLM-as-a-judge evaluators calibrated against the SME-scored ground truth, enabling continuous evaluation at scale.

\subsection{Conclusion}

We presented \threatforest{}, a multi-agent system that automates threat modeling from source code repositories to MITRE ATT\&CK-mapped attack trees with evidence-based mitigations. Our hybrid TTP mapping approach combines domain-specific embeddings with LLM refinement, and our verifier pattern provides quality gates without LLM cost.
